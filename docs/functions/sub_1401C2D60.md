# sub_1401C2D60

- **Address:** `0x1401C2D60`
- **Area:** [Save data](../areas/save-data.md)
- **Prototype:** `void sub_1401C2D60(SaveLoadScreen *screen, ...)`
- **Callers:** `sub_1401C2D20` (one site)
- **Callees:** `SaveSlots_LoadFromFile`, `sub_1400C4214`, `SaveSlot_LoadToLive`, `sub_140257354`, `sub_1402D03D8`, `sub_1401C34B4`

Confidence tags: **V** decoded, **M** measured, **I** inferred, **?** unknown.

## Purpose

The save/load screen's main state machine: it builds the slot list from the container, then loads, confirms or cancels according to the screen's state word.

## Behavior

- V: one state (case 4) calls the manual-slot loader, which is what makes the whole 50-slot image resident when the screen opens.
- V: the load state calls the slot loader and, when the slot's situation byte at `+282` is 1, the resume materialiser instead of a plain load.
- V: it also requests the resume parts and runs the post-load reconciliation step.
- V: it calls the load screen's list setup to decide which lists (enhanced, classic, autosave) to build from the files that exist.
- V: it is reached once from the screen's update wrapper (`sub_1401C2D20`), so all of its states run under the screen's own tick.
- I: the state numbering is the screen's page machine, not a save state; the save-related work is concentrated in two of the states.
- ?: the full state table; only the states that touch the save system were read.
