# sub_1400367F4

- **Address:** `0x1400367F4`
- **Area:** [Save data](../areas/save-data.md)
- **Prototype:** `?` (vtable slot 24 of the save manager)`
- **Callers:** none found — installed in the manager's vtable
- **Callees:** `sub_1400366B0` (exists), `sub_140036AE0` (open), `sub_140036BD4` (delete), `sub_140073918` (mkdir), `sub_14002620C`

Confidence tags: **V** decoded, **M** measured, **I** inferred, **?** unknown.

## Purpose

The mount machine: a six-state routine that creates the save folder, then probes, opens and if necessary deletes the containers the game knows about (`AUTOENHANCED`, the numbered set `0001` to `0005`, and `SYSTEM`).

## Behavior

- V: state 0 creates the save folder through the mkdir helper, on the primary root.
- V: the following states walk the known area names in order: the autosave container, the numbered names 1 to 5 and the system container.
- V: for each area it asks the existence probe, opens what is there and can delete an area file through the delete routine.
- V: it is a vtable slot, never called directly, so no caller list exists in the code.
- V: none of the numbered containers exists in the owner's save sets, so on a normal install only the autosave and system steps do anything.
- I: this machine is what makes a save folder appear on a first run even before any save is written.
- ?: what the numbered 0001..0005 containers are for; no manual-slot path reads them.

## Notes

The delete step is the reason the takeover design has to treat deletion as part of the mount, not only as a menu action.
