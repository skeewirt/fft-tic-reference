Confidence tags: **V** decoded, **M** measured, **I** inferred, **?** unknown.

## Purpose

Computes the CRC-32 checksum the save format stores in every entry header: the manual-slot payload, the resume entries and the settings block are all sealed with it.

## Behavior

- V: it is the platform CRC-32: reflected polynomial 0xEDB88320 (baked into the table data, not an immediate), a slicing-by-4 table of four 0x400-byte planes based at 0x14065D6E0 (read at +0, +0x400, +0x800 and +0xC00), and a caller-supplied seed (zero at every site read).
- V: it takes a seed, a buffer and a byte length and returns the 32-bit result; it is a leaf with no global state of its own.
- V: the four call sites are the entry attach check (`sub_140033DA4`), the resume-entry writer (`sub_1400C3140`, which stores the result at object `+12`), the settings writer (`sub_1400C3814`) and the manual-slot flush (`SaveSlots_StoreToFile`).
- V: the checksum covers the payload only; the 16-byte entry header that carries it is excluded, which is why the writer computes it before the header is built.
- I: because the same routine seals every container, a replacement writer must reproduce it exactly or the game's attach check rejects the entry before any of its fields are looked at.

The polynomial and table base come from the save-container research; the body itself reads four 0x400-byte table planes, so it is the slicing-by-4 form.
