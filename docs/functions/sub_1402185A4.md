## Purpose

The save frame step: it runs one of store, load or image-to-cache per frame, according to the command word of the save manager object (`qword_140D405B8`).

## Behavior

- V: the command word at manager+260 is read and exactly one case runs: 1 store, 2 load, 3 copy the manager image into the slot cache.
- V: the store case calls SaveSlots_StoreToFile, which moves the cache into the manager image, CRCs it, queues fftsave.bin and requests the PNG write.
- V: the load case first asks whether the enhanced or classic PNG exists, then calls SaveSlots_LoadFromFile.
- V: the image-to-cache case moves 0x1EA488 bytes, the whole fifty-slot image.
- V: sub_140218C04 runs only when the save manager is absent (load and image-to-cache commands) or `dword_142E7FB78` is non-zero (image-to-cache); a failed existence check in the load case just clears the command, sub-state and the low dword of `xmmword_142E7FB40`, with no fallback.
- I: sub_140218C04 copies the flat image and reads the legacy per-slot files (its body is not read here).
- V: one step per frame on the game thread; a sub-state at manager+264 tracks where the current command is.
- V: it does not block on the file: between sub-steps it waits while the save request object's busy flag
  (qword_140C69698 +0x188) is set; the PNG read and write run in the container state machine over later frames.
- I: this is the single gate for all slot I/O: no other function both reads and writes the container.
