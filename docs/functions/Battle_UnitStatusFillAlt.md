## Purpose

Builds and animates one of four variants of the battle unit status panel: it fills the panel's attribute record, places its sprite cells, draws ten number fields into two staging buffers, copies them into Vram, and redraws once a frame until the task is asked to close. The `mode` argument selects which shared stat block, number table, cell row and draw-buffer pair the variant uses.

## Behavior

- V: the four variants are the four tail calls: `BattleTask_Slot13Entry` (mode 0, at 0x140229D7C), `BattleTask_ActorForecastPanel` (mode 1, at 0x14022A01C), `BattleTask_TargetForecastPanel` (mode 2, at 0x14022A197) and `sub_140229D84` (mode 3, at 0x140229DCD). Because all four are tail calls, the panel runs in the caller's scene-task slot and continues after the caller's one-shot setup has finished.
- V: the first argument is a four-word block that positions the panel. Words 0 and 1 are the left and top edge, added to every corner of the panel frame; words 2 and 3 are added only to the right and bottom edges, i.e. they extend the box. Word 0 is the only word that differs between the four blocks (0x008C, 0x0089, 0x0157, 0x0151); word 1 is 0x00AA and words 2/3 are 0x0023/0x0034 in all four. Word 0 is a screen coordinate, not a text id.
- V: the fourth argument is one of two shared stat blocks: 0x1407832A0 for modes 0 and 1, and 0x140783320 for modes 2 and 3. The word at block +0x0A is read as a battle-unit-table slot: a value above 20 selects fallback constants, otherwise it indexes the battle unit table (512 bytes a slot), and it is also the unit argument of the portrait lookups. `sub_140226E44` fills the first block from the acting unit's preview slot (`BattleAction_StartScript`'s actor slot) and the second from the target slot, so the blocks are the actor-side and target-side stat blocks.
- V: the stat block is a scratch copy of the preview unit, refilled by `sub_140226E44` (through `sub_140226CA0`) immediately before each of the four variants runs. It holds level at +0x00, the team/auto code at +0x02, the value `BTurn_ForecastIndex` returns (plus one when it is not negative) at +0x04, a live unit count at +0x06, EXP at +0x08, current and maximum HP at +0x0C/+0x10, current and maximum MP at +0x12/+0x16, a 0..100 value at +0x18 and the constant 100 at +0x1C. The +0x18 value is the unit's byte +0x41, or 100 when the unit's byte +0x1B8 is set. This function also rewrites the +0x02 code each frame from unit bytes +0x1EE and +0x1EC (1 when bits 0x30 of +0x1EE are set, 2 when bits 0x38 are clear, 3 when +0x1EC is non-zero) and caps +0x18 at 100. The HP, MP and +0x18 values are each the first and third word of a three-word group (+0x0C/+0x0E/+0x10, +0x12/+0x14/+0x16, +0x18/+0x1A/+0x1C).
- V: the third argument is a table of ten 32-byte number-field records. Each record holds a pen position, an inline field name, a digit count, a style word and a pointer to the value it draws. The inline names are, in order, hp, hpmax, mp, mpmax, wt, wtmax, at, atmax, level and exp.
- V: the four tables are duplicates in pairs. Mode 0 uses the unnamed table at 0x140808200 (reached as `&a4_0[2]` from the block at 0x1408081FC); mode 1 uses 0x140808480 (`tbl_UiStatusNumbersActorB`), which is byte-identical to it. Mode 2 uses 0x140808580 (`tbl_UiStatusNumbersTargetB`), byte-identical to the mode-3 table at 0x140808340. The pairs differ only in which stat block their value pointers address: the actor pair points into 0x1407832A0, the target pair into 0x140783320. Modes 0 and 1 therefore draw the same ten numbers.
- V: the first six fields (hp to wtmax) are drawn into the first staging buffer with `NumberFields_Draw` for every mode. The last four go into the second buffer, and this is where the three mode families differ: modes 0 and 3 draw at/atmax and then level/exp, mode 1 draws only at/atmax, and mode 2 draws none of them. Instead mode 2, when the unit's word at +0x14 is below 0x200, draws that index as a text line from text pool 14 through `sub_140243364`.
- V: the two staging buffers share one 1792-byte allocation, the second at +1024. Both are cleared, drawn by `NumberFields_Draw` and copied to their own Vram page by `VramPage_CopyRect`. The block is allocated on the first frame and freed at the start of the second; the two Vram pages are freed when the task ends.
- V: the draw record is one of four pairs of 1800-byte panel draw blocks at 0x142FF4280. A byte table yields 0, 2, 4 and 6 for modes 0..3, and each frame uses one block of the pair (`k & 1`), so the four variants never share draw state.
- V: the cell layout is a per-language table (`tbl_UiStatusPanelLayoutsDefault` and the Lang0, Lang2, Lang3 variants) of eight pointers. The first four are one cell list per mode, of six-word cells; the last four are two seven-entry lists, one shared by the two actor modes and one by the two target modes. Modes 0 and 3 place four cells, mode 2 two (a third when the preview id is present) and mode 1 one fixed cell plus two. Mode 1 then calls `UnitPanel_FillEffectLine` for the effect line.
- V: the attribute setters write the battle UI panel record reachable through 0x143CD9DA8. Each is given the panel index (the mode, or 6 for mode 0 in state 91), so the mode selects the panel. They set the name, level, EXP, the HP and MP pairs, the +0x18 value, Brave, Faith, zodiac, the flags bit and the team/auto code. I: the forecast tasks' projected HP/MP words land in the first 212-byte block for mode 1 and the second for mode 2 (rests on their two direct writes); how the setters map the other panel indices to blocks is not visible here.
- V: when the mode is 0 and `g_BattleState` is 91, the attribute setters and the per-frame draw calls use panel slot 6 instead of slot 0. The rest of the body is unchanged.
- V: each frame the task calls `SceneTask_FindTag(21)`. When a running task carries tag 21 it switches the panel background to palette set B, writes 64, 80 and 112 into three bytes of the draw block instead of 128, and halves the palette values of the three segments it scales from the stat block's value/max pairs; with no such task it uses palette set A at full brightness.
- V: the frame ends with `SceneTask_WaitFrame`. `word_142FF3CAC` advances while the panel settles in (it reads 0 once the offset has reached 0) and on every step of the closing path. `word_142FF3CA8` advances only when a field of the current task's slot equals 17 (I: the tag the battle presentation programs give this variant in programs 2 and 3; program 6 gives it 37). The exit path zeroes both under the same test.
- V: closing is driven by the word at +16 of the task's own slot in the scene-task table; `sub_140227558` (the task that draws the banner) polls the same word. While it is 0 the panel settles from its 132-unit offset in decreasing steps (22, 20, 18 and so on) and keeps drawing; once it is non-zero the offset grows by 30 a frame until it passes 128, and the task then frees the Vram pages and calls `SceneTask_Terminate`. When the close word is non-zero, mode 0 with `qword_140D46B38` equal to 19 takes the closing path at once; that global rests at -1 and no direct writer was found.
- V: the callers do the work their variant needs before the tail call. `BattleTask_Slot13Entry` refreshes the scene and seeds the two panel counters. `BattleTask_ActorForecastPanel` runs the secondary-action preview, waits two frames, refreshes and copies the predicted HP/MP into the UI manager. `BattleTask_TargetForecastPanel` waits two frames, swaps the two preview unit slots, refreshes twice, restores them and copies the prediction. `sub_140229D84` only refreshes and seeds its own panel counter.
- V: the battle presentation programs place the variants. Programs 2 and 3 start mode 0 as their last task (slot 13, tag 17) beside the banner task (slot 10, tag 16); program 3 adds `sub_14022A19C` in slot 11. Program 4 starts mode 3 alone. Program 5 starts modes 1 and 2 together (slots 12 and 13, tags 19 and 18). Program 6 starts mode 0 beside `sub_14022A19C`, with tags 37 and 36.
- I: modes 1 and 2 are the two halves of one forecast (rests on program 5 starting them together in adjacent slots and tags, and on mode 1 alone drawing the effect line). The A (first) and B (second) labels inside each role pair come from that pairing: 0 and 3 run alone, 1 runs with 2. The visible titles are not established.
- ?: which task kind carries tag 21 (no battle presentation record carries it); what battle state 91 is; what the value 19 of `qword_140D46B38` means and who sets it; what `dword_140782D14` is; what the two panel counters drive outside this task; the visible titles of the four panels.

## Notes

Whole body read (5546 bytes), together with the four call sites, the four position blocks, the four ten-record number tables, the two stat blocks and the per-language cell tables. Corrects the starting notes in three places: the first position word is the panel's left edge, not a text id; mode 0's number source is the unnamed fourth table at 0x140808200, not an unresolved pointer; and earlier versions of the `BattleTask_Slot13Entry` sheet called its tail target a 'battle message/event runner'; that label belongs to the sibling banner task `sub_140227558`, not here. The function reads the battle unit table directly for the name, job, Brave, Faith, zodiac, status bytes and level / EXP, and takes the numbers it draws from the stat block that `sub_140226E44` refills; the 0..100 field named wt is the field `Battle_UnitStatusFill` computes as a CT fallback (unit byte +0x41, or 100 when unit byte +0x1B8 is set).
