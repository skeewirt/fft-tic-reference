# SaveLoadScreenFlow

- **Kind:** flow
- **Area:** [Save data](../areas/save-data.md)

Confidence tags: **V** decoded, **M** measured, **I** inferred, **?** unknown.

## Summary

The save/load screen's ordered path. One UI agent opens behind a fade, shows a saving overlay while it loads the save index, creates the list addon, builds the automatic rows and the tab, then rests in state 0 while the list addon sends events. The events branch to load, save, erase, the New Game + source pick, the close path, or a deferred switch that waits before entering the load or source-pick state.

## Behavior

- V: the screen is one agent with eleven states; state 0 is a no-op resting state, states 1..4 bring the screen up, states 5..8 act, state 9 closes and state 10 defers a target state. The state-to-handler table is the UISaveLoadStates registry; the second block's three used states are the UISaveLoadDialogStates registry.
- V: the mode field at +0x40 is written three ways: UISaveLoad_Open writes 2 for the load path, TitleScene_Update rewrites it to 4 for New Game +, and sub_140182DF8 writes 1 with a situation value for the save path. State 3 collects the five headers only when bit 1 is set; state 4 maps bit 0/bit 2 to the tab.
- V: tab 0 and tab 1 both scan all 50 cache slots; tab 0 adds one entry created by sub_140186390 first, tab 1 copies the automatic vector first, and tab 2 neither copies the vector nor adds the extra entry. Tab 2 keeps only valid slots whose +0x119 byte is non-zero and whose +0x11A situation byte is 5 or 0.
- V: the automatic vector is filled by SaveLoadList_BuildAutoEntries from the five 264-byte headers; only headers with the FFTI magic, dword 122 at +4 and a kind below 2 at +0x0C become rows. Only tab 1 copies that vector into the visible list.
- V: the list addon is the event source. The agent forwards its events only while the list addon exists and the event source id matches; the event map stores the selection at +0xE4, the load flag at +0xF4 and the target state at +0xF0.
- V: load and save use different completion paths: load writes g_GlobalWork+102 and +104 when it finishes, while save writes the cache slot and then reloads the save index through the second block. Erase writes 0xFF over the whole cache slot and reloads the index too.
- V: state 10 is a wait. It sets no prompt and stores no new choice; it calls sub_1401D6DB0 for UI agent slot 13 with value 1 and then enters +0xF0 (5 for load, 8 for source pick). The initial slot value 23 skips the wait.
- V: g_GlobalWork+128 is written only by state 8: the title seeds it with -1 and reads it after the screen closes. State 5 (load) writes g_GlobalWork+102 and +104 as flags. I: the load path therefore uses a different field, so the two callers share the screen without sharing a result field.
- I: tab 0 is the save list, tab 1 the load list with automatic slots and tab 2 the New Game + source list (rests on the three open modes and the tab compositions; on-screen captions were not read).
- I: the mode-1 path is the in-game save: sub_140182DF8 is called by a save helper and a blocking menu helper, sets bit 0 and stores the situation value that state 6 writes (rests on those two callers and on SaveSlot_WriteFromLive).
- ?: the on-screen labels of the tabs and prompts; which UI agent occupies slot 13 that state 10 tests; what guide 235 is; whether the dialog block's state 3 was intended.

## Notes

Read: the open, the ten state handlers, the event map, the pause callback, the list builders and the title's -1 seed. Three handlers have no published sheet yet (sub_1401836F0 state 2, sub_140183ED0 state 9, sub_140183FA0 state 10), so their steps point at their UISaveLoadStates entries and name the function in the text. The registry lists state 8 as UISaveLoad_StateNewGamePlus while its page is UISaveLoad_StateSourcePick. In sub_140183658, phase 1 does call sub_1400C480C as a guard. The save step's row search looks for +0xE4 after the save branch has set it to -1, so the ordinary save does not leave the cursor on a row.
